## Q1. MCP의 읽기·쓰기 범위와 승인 지점을 어떻게 나눴나요?

이슈·코드·PR 조회는 원격 상태를 바꾸지 않으므로 읽기 작업으로 분류했다.
이슈·PR·리뷰 생성, 브랜치 갱신과 병합은 원격 상태를 바꾸므로 사용자의 명시적
지시가 필요한 작업으로 분류했다. 실제 MCP 검증에서는 초기화, 도구 목록 조회와
이슈 #1 읽기만 수행했다. [실제 응답](evidence/w2/mcp-live-response.json)을 남겼다.

이 구분은 작업 정책이다. MCP 등록만으로 쓰기 도구가 차단되거나 사람 리뷰·CI 확인이
강제되는 것은 아니다. 토큰 scope와 호스트의 권한·승인 설정을 별도로 적용해야 한다.
이번에 사용한 gh 인증은 자식 프로세스 환경에만 전달했고 토큰을 저장하지 않았다.

## Q3. Playwright가 무엇을 검증하고 무엇을 검증하지 못하나요?

태그 필터 테스트는 게시글에서 추출한 태그 버튼 노출, AI 태그에 해당하는 정확한
제목 목록, 전체 버튼으로 원래 목록·순서 복원, 선택한 태그 재클릭으로 초기화를 검증한다.
기존 홈페이지·상세 페이지 테스트도 함께 실행한다.

현재 동일 테스트를 구현 전 커밋 `07e9f23`의 별도 worktree와 현재 구현에서 실행해
Red/Green을 재검증했다. 이 결과는 과거 TDD 개발 순서를 입증하는 기록과 구분한다.

시각적 완성도, 모든 화면 크기, 스크린 리더 접근성, 대규모 데이터 성능과
각 AI 제품에서 agent·hook이 로드되는지는 이 E2E의 검증 범위가 아니다.
현재 Playwright는 개발 서버를 사용하므로 프로덕션 서버 실행 검증과도 구분한다.
