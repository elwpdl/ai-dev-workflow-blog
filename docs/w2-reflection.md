# 2주차(W2) 근거형 질문 답변 및 회고

### Q1. 연결한 MCP에서 읽기 전용으로 충분한 지점과 쓰기 권한이 필요한 지점을 어떻게 나눴나요?

- **읽기 전용 (Read-Only) 지점 - 자율 실행 허용**:
  - `search_code`, `search_issues`, `get_issue`, `get_pull_request`, `list_pull_requests`
  - **분리 기준**: 원격 저장소의 영구적인 상태(State)나 기록을 변경하지 않고 단순 정보 수집 및 컨텍스트 파악을 위한 도구입니다. 부작용(Side-effect)이 없으므로 에이전트가 사람의 승인 없이 자율적으로 호출할 수 있습니다.
- **쓰기/변경 (Write / Mutate) 지점 - 사람 승인 필수 (Human-in-the-loop)**:
  - `merge_pull_request`, `update_pull_request_branch`, `create_pull_request_review`
  - **분리 기준**: 메인 브랜치(`main`), 배포 파이프라인, 협업 팀원들에게 직접적인 영향을 미치는 비가역적 액션입니다.
  - 특히 PR 병합(`merge_pull_request`)은 모든 자동화 테스트(CI) 통과 여부와 사람 리뷰어의 최종 승인이 확인된 후에만 실행되도록 엄격히 권한을 제한했습니다.

### Q2. claude.md에 브랜치·커밋·PR 규칙을 넣기 전과 후에 AI의 결과물이 어떻게 달라졌나요?

- **규칙 적용 전**:
  - AI가 `main` 브랜치에 직접 코드를 커밋하거나, 임의의 브랜치명(예: `dev`, `my-feature`)을 사용하여 어떤 이슈를 해결하기 위한 작업인지 추적하기 어려웠습니다.
  - 커밋 메시지가 모호하거나 일관성이 없고(`update file`, `fix`), PR 템플릿의 존재를 알지 못해 최소한의 설명만 남긴 채 PR을 올려 인간 리뷰어의 재확인 비용이 컸습니다.
- **규칙 적용 후**:
  - 이슈 번호를 기반으로 한 정형화된 브랜치(`feature/1-tag-filter`)를 자동으로 생성하여 작업 컨텍스트를 완벽히 격리했습니다.
  - Conventional Commits 규약(`feat:`, `fix:`)을 철저히 준수하여 변경 이력이 명확해졌습니다.
  - `.github/PULL_REQUEST_TEMPLATE.md`의 구조(What, Why, How, Test Evidence, Checklist)를 스스로 채워 넣고 이슈 번호를 자동 연결(`Closes #1`)하여 협업에 최적화된 고품질 PR을 생성했습니다.

### Q3. Playwright 시나리오가 이 기능의 무엇을 보장하고, 무엇은 여전히 보장하지 못하나요?

- **Playwright 시나리오가 확실하게 보장하는 것**:
  - **실제 브라우저 환경에서의 엔드투엔드 인터랙션**: 사용자가 태그 버튼을 클릭했을 때 DOM이 정상 반응하는지, 필터링 후 화면에 노출된 포스트들이 모두 해당 태그를 가지고 있는지, '전체' 버튼 클릭 시 원래 목록이 복원되는지를 실제 브라우저 런타임에서 증명합니다.
  - **기능 회귀(Regression) 방지**: 향후 홈 화면이나 CSS 레이아웃을 리팩토링할 때 태그 필터 동작이 깨지는지를 `npm test` 한 번으로 즉시 감지합니다.
  - **TDD 사이클 입증**: 구현 전 실패(Red) 로그와 구현 후 통과(Green) 로그를 남김으로써 해당 기능이 실제로 테스트를 통해 검증되었음을 객관적으로 증명합니다.
- **여전히 보장하지 못하는 한계점**:
  - **시각적 완성도(Visual Regression)**: 태그 버튼의 색상 대비, 모바일 뷰포트에서의 여백과 줄바꿈 자연스러움 등 심미적 디자인 품질은 검증하지 못합니다.
  - **대규모 데이터 렌더링 성능**: 포스트 수가 수천 개로 증가했을 때 브라우저 렌더링 랙이나 메모리 점유율을 잡아내지 못합니다.
  - **웹 접근성(a11y)**: 스크린 리더 친화성, 키보드 Tab 탐색 순서 및 ARIA 상태 변경 알림 등은 추가적인 a11y 전용 테스트가 필요합니다.
