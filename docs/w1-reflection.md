# 1주차(W1) 근거형 질문 답변 및 회고

---

### Q1. claude.md에 반드시 있어야 하지만 일반 README에는 없어도 되는 정보는 무엇인가요?

- **README.md**는 주로 사람(동료 개발자, 오픈소스 기여자)을 위한 문서로, 프로젝트의 비전, 아키텍처 개요, 스크린샷, 로컬 실행 방법처럼 사람이 맥락을 능동적으로 해석할 수 있는 정보를 제공합니다.
- 반면 **CLAUDE.md(프로젝트 헌법)**는 자율적으로 코드를 수정하는 **AI 에이전트의 결정 권한과 행동 반경을 물리적으로 구속하는 기계 지침서**입니다.
  - **절대 수정 금지 경로 (Protected Paths)**: `.env*`, `.github/workflows/*`, `package-lock.json` 등 AI가 임의로 건드릴 경우 보안 누출이나 CI/채점 파이프라인 마비로 이어지는 경로를 명확히 고정합니다. (사람 개발자는 상식적으로 건드리지 않지만 AI는 자의적 판단으로 수정할 위험이 있습니다.)
  - **명시적 완료 조건 (Definition of Done)**: AI가 작업을 조기 종료하거나 자의적으로 "완료"라고 선언하지 못하도록 `npm run build`, `npm run lint`, `npm test`를 필수 검증 절차로 못박습니다.
  - **엄격한 기술 제약 및 스키마**: Next.js 15+ App Router 규약(`Promise<params>`), 마크다운 Frontmatter 스키마(`title`, `date`, `tags`) 등 AI가 다른 프레임워크의 관습을 섞지 못하도록 저장소 전용 제약을 기계적으로 기술해야 합니다.

### Q2. PreToolUse로 막아야 하는 변경과 PostToolUse로 뒤처리하면 되는 변경을 어떻게 나눴나요?

- **PreToolUse로 막아야 하는 변경 (사전 차단 / Fail-Fast)**:
  - **비가역적이거나 보안/인프라에 치명적인 변경**: 파일 수정이 일어나는 순간 되돌리기 어렵거나 부작용이 큰 경우입니다.
  - *적용 대상*: `.env*` 시크릿 유출/덮어쓰기, `.github/workflows/` CI 설정 변조, `package-lock.json` 무단 변조, `.git/` 메타데이터 접근 등.
  - 도구가 파일 시스템에 쓰기를 시도하기 직전에 **non-zero exit code (코드 2)**로 중단시켜, AI 모델에게 명확한 거부 사유(stderr)를 전달하고 즉시 다른 대안을 강구하도록 합니다.
- **PostToolUse로 뒤처리하면 되는 변경 (사후 검증 및 피드백 / Auto-Correction Loop)**:
  - **작업 자체는 허용되지만, 코드 스타일이나 품질 표준에 미달할 수 있는 변경**:
  - *적용 대상*: TypeScript/JavaScript 파일 수정 후 ESLint 린트 오류, 포맷팅 어긋남, 누락된 세미콜론 등.
  - 파일 저장이 완료된 직후 린터를 자동으로 실행하여, 코드에 문제가 생겼을 때 AI가 즉각 에러 로그를 보고 스스로 교정(Self-healing)할 수 있도록 피드백 루프를 제공합니다.

### Q3. Hook을 붙였는데도 막지 못한 실수는 무엇이고 다음에 어떻게 막을 계획인가요?

- **막지 못한 실수와 한계점**:
  1. **도구 우회(Tool Bypassing) 가능성**: 파일 수정 도구(`FileEdit`, `FileWrite`)의 경로는 차단했지만, AI가 `Bash` 도구를 사용하여 `echo "SECRET" > .env` 또는 파이썬 스크립트 실행 등으로 우회 쓰기를 시도할 경우 단순 경로 기반 매칭을 뚫을 수 있습니다.
  2. **의미론적/비즈니스 논리 오류**: 문법상 오류가 없고 린트도 통과하지만, 블로그 포스트의 날짜 정렬이 뒤틀리거나 필수 마크다운 태그가 어색하게 들어가는 등의 논리적 결함은 파일 수준 Hook만으로 검증할 수 없습니다.
- **향후 개선 계획**:
  1. **Bash 명령 정적 필터링 확장**: PreToolUse Hook에 `tool_name == "Bash"` 검사기를 추가하여 커맨드라인 내 위험 키워드(`.env`, `git push --force`, `rm -rf`)를 사전에 정규식으로 차단합니다.
  2. **W2 Playwright E2E 검증 통합**: W2에서 도입할 E2E 테스트를 커밋 전/PR 전 단계에 필수 연결하여 실제 브라우저 렌더링 관점에서 논리적 결함까지 사전에 검증합니다.
  3. **심층 방어(Defense in Depth) 구축**: 에이전트 Hook뿐 아니라 Git 자체의 로컬 `pre-commit` 훅(Husky/lint-staged)과 GitHub Actions CI 브랜치 프로텍션 룰을 다중 안전망으로 결합할 계획입니다.
