# W1–W4 운영 및 자동화 회고

## 이번 사이클

게시글 검색을 PRD로 정의하고 기능 #5, 인수 검증 #6, 운영 기록 #7로 분할했다.
`feature/5-w4-search`에서 기존 태그 필터와 결합하고 통합 PR로 추적한다.
실행 증거와 PR 링크는 [W4 인덱스](evidence/w4/README.md)에 모은다.

## 자동화가 줄인 병목과 근거

- W1: 공통 헌법에 금지 경로와 검증 명령을 고정하여 매 작업마다 확인할 기준을 제공했다.
  W4에서도 실제 Hook 어댑터의 보호 경로 probe가 deny를 반환했고 수정 후 린트가 통과했다.
  모든 모델의 호스트가 자동 호출했다는 증거는 아니다.
- W2: [실제 MCP 응답과 이슈/PR 연결](evidence/w2/README.md)을 기반으로 W4의 이슈별 인수
  조건을 PRD와 E2E에 연결했다. 기존 태그 테스트를 재사용해 검색 추가 후 회귀를 점검했다.
- W3: [실제 AI 리뷰](evidence/w3/README.md)는 URL breadcrumb의 민감 쿼리 잔존을 발견했다.
  기존 관측 전송 검증을 W4에서도 다시 실행해 변경과 함께 회귀가 없는지 확인했다.
- W4: 검색 입력 부재로 Red를 먼저 확인했고 구현 후 기존 4개와 신규 5개 E2E가 통과했다.
  사람의 수동 검색 반복을 테스트로 대체할 수 있지만 절약 시간은 측정하지 않았다.

## 새롭게 생긴 병목

- 무료 AI 리뷰는 사용량·서비스 대기에 영향을 받는다. 유료 크레딧을 사용하지 않으며
  요청 접수, 실제 리뷰 완료, 테스트 통과, 병합 여부를 별도로 기록해야 한다.
- 개발 서버 E2E만으로 Docker 배포를 보장할 수 없다. 별도 이미지로 검색·HTTP 응답·
  기본 비활성 관측 probe를 확인했다. 실제 클라우드 배포와 트래픽은 이번 범위가 아니다.
- 임시 디렉터리 로그가 이어진 세션에서 사라져 검증을 재실행했다. 이후 결과는 저장소의
  증거 경로에 바로 기록했다. Red는 실행 당시 도구 출력 발췌만 남았고 전체 원본으로 표시하지 않았다.
- 자동 리뷰의 마크다운·운영 문서 지적도 실제 코드 결함과 분리해서 판단해야 한다.
  AI 리뷰를 승인 권한이나 보안 보증으로 취급하면 오히려 확인 절차가 약해진다.

## 다른 팀원에게 넘기기 위한 절차와 개인 의존성

| 항목 | 현재 개인 의존성 | 인계 시 조치 |
| --- | --- | --- |
| GitHub | elwpdl 저장소 및 현재 gh 로그인 | 본인 계정으로 로그인, remote와 이슈/PR 권한 확인 |
| CodeRabbit | 개인 OAuth 및 GitHub App 설치·무료 한도 | 본인 인증/설치 상태 확인, 유료 사용은 별도 승인 |
| Sentry | djhobby 조직·프로젝트 및 로컬 컨테이너 환경 | 팀 프로젝트 접근 부여 또는 새 프로젝트 DSN을 사용자 환경에 설정; 토큰을 문서에 복사하지 않기 |
| MCP | 현재 gh 인증을 사용하는 실행 환경 | docs/agent-configuration.md의 도구별 경로·권한을 확인하고 실제 읽기 호출 재검증 |
| 런타임 | mise의 Node 버전과 로컬 Docker | mise 설정과 npm ci 사용, Docker 실행 권한 확인 |
| 테스트 서버 | localhost:3000 재사용 가능 | 다른 저장소 서버가 없는지 확인; CI에서는 새 서버 사용 |
| Hook·역할 | 설정 정의와 제품별 지원 차이 | test:hooks/test:agent-config 실행 후 실제 사용하는 모델에서 호출 별도 확인 |
| 리뷰 workflow | docs/workflows 명세만 존재 | 설치가 허용된 저장소에서 검토 후 적용; 여기서는 보호 경로를 수정하지 않기 |

새 팀원은 README → AGENTS.md → docs/agent-configuration.md → docs/prd.md 순서로 읽고,
`npm ci`, `npm run build`, `npm run lint`, `npm test`, `npm run test:hooks`,
`npm run test:agent-config`, `npm run test:monitoring`으로 기준 상태를 재현한다.
Docker는 compose.yaml을 사용하되 관측 환경은 개인/팀 환경에서 주입한다.
검색은 외부 API나 환경 변수 없이 동작한다. W4 검증용 컨테이너는 DSN 없이 3101에서 실행했다.

## 근거형 질문 답변

### 1. 성공 기준 중 확인된 것과 아직 확인하지 못한 것은?

제목·요약·태그 검색, 대소문자·공백 처리, 태그 AND 조합, 초기화·포커스, 빈 결과,
상세 이동과 두 화면 폭을 E2E로 확인했다. 실제 사용자의 탐색 시간, 사용률, 스크린리더
실기 테스트, 모든 브라우저, 대량 데이터 성능은 미확인이다. 성공 기준을 사용자 성과로 확대하지 않는다.

### 2. 헌법·Hook·리뷰에서 도움이 되거나 방해가 된 요소는?

보호 경로와 설치된 Next.js 문서 확인 규칙이 범위를 고정했고 Hook은 금지 경로 입력을
차단했다. E2E는 태그 해제 시 검색어 보존과 검색 초기화 시 태그 보존을 반복 검증했다.
반면 제품별 Hook 전달 형식, 무료 리뷰 대기, 증거 보존은 추가 운영 작업이다.
리뷰 결과의 실제 내용과 처리 상태는 W4 증거에 남기며 미실행 사항을 완료로 취급하지 않는다.

### 3. 재사용하려면 무엇을 문서화하거나 제거해야 하는가?

개인 계정·Sentry 프로젝트·로컬 포트와 인증을 팀 환경으로 대체해야 한다.
DSN/토큰 자체가 아닌 주입 방법과 접근 권한을 전달하고, 실제 agent 호출 및 CI 설치는
새 환경에서 별도 검증해야 한다. 재사용 지침과 관측 한계는 기존 설정/관측 문서에 연결해
중복 설정을 줄인다. 개인 환경이 그대로 복제된다는 전제는 두지 않는다.
